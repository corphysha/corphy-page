## 重大頭條

### Citrix NetScaler 兩個已遭利用的 RCE 零時差漏洞

Cloud Software Group 在 [NetScaler 安全公告](https://support.citrix.com/external/article/CTX697096/netscaler-adc-and-netscaler-gateway-security-bulletin)中確認 CVE-2026-88771 至 CVE-2026-88778，並指出 CVE-2026-88771 與 CVE-2026-88772 已在未修補部署上遭到利用。[watchTowr 的技術整理](https://watchtowr.com/intelligence/citrix-netscaler-adc-citrix-netscaler-gateway-remote-code-execution-cve-2026-88771/)將 CVE-2026-88771 描述為未驗證輸入導致的任意命令執行，受影響版本的預設設定也可能暴露，CVSS 4.0 基本分數為 9.5。CVE-2026-88772 則是記憶體溢位，DTLS 啟用時可造成遠端程式碼執行或阻斷服務，VPN virtual server 的 DTLS 預設為啟用。[BleepingComputer 的事前報導](https://www.bleepingcomputer.com/news/security/citrix-admins-warned-to-shut-down-netscalers-over-2-exploited-zero-days/)記錄了研究人員與國家級 CSIRT 在公告前要求組織隔離 NetScaler 的情況。

這組漏洞的重要性在於 NetScaler 位於遠端存取、VPN、AAA 與負載平衡邊界，入侵後的權限位置通常比一般應用程式更接近內網入口。官方固定版本為 14.1-73.37、13.1-64.23、14.1-73.37 FIPS，以及 13.1-37.279。官方沒有提供可取代升級的通用 workaround，維運順序應是先保存支援包、紀錄與快照，再檢查入侵跡象，最後升級並輪替可能被讀取的憑證。CVE-2026-88778 另外需要啟用 Enhanced ISN Generation，單純更新套件不會完成這項設定修補。

### Samba 4.25 把持久檔案控制代入叢集高可用性

[Samba 4.25.0 官方 release notes](https://www.samba.org/samba/history/samba-4.25.0.html)在 9 月 24 日發布，這是 4.25 系列的第一個穩定版本。[LinuxCompatible 的整理](https://www.linuxcompatible.org/story/samba-4250-released-persistent-handles-ceph-smb-export-and-cluster-ha/)與 [PBXScience 的獨立說明](https://pbxscience.com/samba-4-25-ships-with-experimental-persistent-handles-and-new-ceph-storage-bridge/)都確認本版加入實驗性的 SMB3 Persistent Handles、cluster functional level、cluster-wide rate limiting，以及 vfs_ceph_rgw。

Persistent Handles 讓 SMB client 在伺服器重啟或短暫中斷後保留可重建的 file handle，目標是支援 VM storage 與 clustered database 等不能輕易重新開檔的工作負載。功能要求 share 走 SMB-exclusive 路徑，並關閉 kernel oplocks、kernel share modes 與 POSIX locking，因此不能把同一個 share 當成一般 Linux 檔案系統與 NFS 共用目錄。狀態同步寫入 durable storage 會增加每次 open、update、lease 與 close 的延遲，官方明確不建議把它當成一般檔案伺服器的預設選項。4.25 也把 domain authentication 的預設加密類型調整為 AES，並以 cluster functional level 1.0 協助混合版本叢集進行受控升級。

### Froxlor 三項高風險漏洞公開，修補版本早已存在但曝光範圍要重查

[CVE-2026-100716 的 CVE Record](https://www.cve.org/CVERecord?id=CVE-2026-100716)在 9 月 26 日更新，描述 Froxlor 2.3.10 以前的 DataDump cron 未完整檢查中間路徑元件，低權限 customer 可以利用 symlink 讓 root-owned cron 對非預期目錄執行 chown -R。CVE record 將此漏洞列為 CVSS 3.1 9.9 Critical，並確認問題在 2.3.12 修正。[Froxlor 的 GitHub security advisories](https://github.com/Froxlor/Froxlor/security/advisories)列出同一批公開的 cron、symlink 與 URL 驗證問題；[ThreatAft 的 9 月 27 日整理](https://threataft.com/articles/froxlor-mass-disclosure-cve-2026-100716-100717-100715)則把事件整理為 CVE-2026-100716、CVE-2026-100717 與 CVE-2026-100715 三項高風險漏洞。

這次的重點不是 9 月 26 日又發布了一個修補版本。[2.3.12 的 GitHub release](https://github.com/Froxlor/Froxlor/releases/tag/2.3.12)早在 8 月 23 日就存在，因此組織不能用「今天才看到公告」推論「今天才需要修補」。真正需要重做的是版本盤點、cron 執行紀錄、產生的 nginx 或 Apache 設定，以及同一主機上其他 tenant 的檔案權限。ThreatAft 表示當時沒有公開 exploit，CVE record 與 GitHub advisory 則足以證明受影響版本與修補版本，不能把「沒有公開 exploit」當成不需處理的理由。

### SageMaker HyperPod Inference Gateway 將 GPU-aware routing 放進 EKS addon

[AWS 的 9 月 24 日公告](https://aws.amazon.com/about-aws/whats-new/2026/09/sagemaker-hyperpod-inference-gateway/)發布 SageMaker HyperPod Inference Gateway，將 GPU-aware request routing 作為現有 HyperPod infrastructure 上的 Kubernetes-native EKS managed add-on。[AWS Machine Learning 技術文章](https://aws.amazon.com/blogs/machine-learning/introducing-amazon-sagemaker-hyperpod-inference-gateway/)說明它由 Envoy Endpoint、Body-Based Router 與 Endpoint Picker 組成，後者依 KV cache utilization、queue depth、LoRA adapter residency、prefix cache hit rate、predicted latency 與 running requests 選擇後端。[AWS News Feed 的同步整理](https://aws-news.com/article/2026-09-24-amazon-sagemaker-hyperpod-inference-gateway-for-scalable-llm-inference)也確認它可搭配 vLLM 與 SGLang，維持 OpenAI-compatible API，不要求應用程式更改 client code。

AWS 自行測試的結果是 mixed GPU generations 與 bursty traffic 下，p99 first-token latency 最多降低 97 至 98%，但這些數字是 AWS 的 benchmark，不是所有模型與流量形狀都能重現的保證。這項產品的實際變化在 routing decision 從一般 Kubernetes load balancing 移到推論狀態，應用程式仍透過同一個 endpoint 發送請求。對平台團隊而言，新的控制面會和 Prometheus metrics、model pool、LoRA cache 以及 EKS addon lifecycle 綁在一起，必須把資料來源與 fallback 行為納入容量測試。

~~~yaml
apiVersion: inference.sagemaker.aws.amazon.com/v1alpha1
kind: InferenceGatewayConfig
metadata:
  name: my-gateway
spec:
  tls: {}
  bbr:
    enabled: true
  schedulers:
    - name: llama-70b
      modelName: "llama-3.1-70b"
      modelSelector:
        matchLabels:
          app: vllm-llama
      targetPort: 8000
      scheduler: llm-d
~~~

## 細節說明

### NetScaler 的暴露面與修補順序

CVE-2026-88771 的前置條件是網路可達性，不需要先開啟額外功能，也不要求有效帳號。這使外部暴露的 ADC、Gateway、VPN 與 AAA virtual server 都應視為優先資產，即使它們沒有明顯的自訂功能。CVE-2026-88772 的條件較窄，但 VPN virtual server 的 DTLS 預設行為讓許多部署仍可能符合條件。官方同一份公告還列出 HTTP request smuggling、URL expression policy bypass、多項 memory overflow，以及 TCP initial sequence number prediction，後者要以設定變更補上 Enhanced ISN Generation。

升級前保存證據是這次事件和一般例行更新的差別。watchTowr 建議先保存 logs、snapshot、support bundle 與 core dump，再做 IOC 檢查與版本更新。更新後仍要把 NetScaler logs 送進 SIEM，並輪替 appliance 曾使用或保存的 password、secret 與 certificate。若 13.1 appliance 的 upgrade path 涉及既有變數，應先依官方與研究報告的版本說明檢查相容性，不要直接把最新 image 視為唯一的變更步驟。

### Persistent Handles 的配置邊界

Samba 4.25 的新功能不是把一個布林值設成 yes 就得到透明故障轉移。官方要求全域 persistent handles 與 share 的 continuous availability 同時啟用，並關閉三項會和本機 POSIX 或 NFS 存取互相衝突的鎖定功能。以下配置只適合專用的 SMB share，不能直接複製到混合存取的既有資料目錄。

~~~ini
[global]
    persistent handles = yes
    persistent handles durability = full_outage

[persistent-vm-share]
    path = /srv/vm
    read only = no
    continuous availability = yes
    kernel oplocks = no
    kernel share modes = no
    posix locking = no
~~~

full_outage 會保留叢集完全停機後重建 handle 所需的 backup state，但每次 handle 狀態改變都會帶來額外的 cluster-wide transaction。partial_outage 可以少做同步工作，代價是所有節點同時離線時 handle 會遺失。這個取捨需要用實際 VM storage 或 database workload 測試，不能只用檔案複製 benchmark 判斷。

### Froxlor 的 root cron 與 tenant 隔離

CVE-2026-100716 的核心問題是 path validation 只看到了最後一段，沒有在 root cron 執行前重新驗證中間元件。若 customer 能在排程與執行之間替換 symlink，root-owned chown -R 可能跨出原本的 webspace。CVE-2026-100715 以相似的 symlink 問題影響 FTP data deletion cron，結果可能是 root 權限的遞迴刪除。CVE-2026-100717 則從 URL userinfo 元件繞過 CRLF 檢查，把未預期內容寫進 nginx 或 Apache vhost 設定。

這三種問題都把 tenant 權限和主機級 cron 的信任邊界接在一起。執行 2.3.12 或更新版本只是第一步，仍要檢查是否曾使用 2.3.10 或更早版本、是否有 customer 具備 export 或 subdomain-create 權限，以及 vhost 產生與 reload 紀錄是否出現異常。由於 2.3.12 在 8 月已發布，套件 registry 或 GitHub release 的目前版本不能證明主機沒有載入過舊版。事件回應應保存 cron、檔案時間、web server 設定與 tenant home 的權限變更紀錄。

### GPU-aware inference routing 的實作方式

HyperPod Inference Gateway 把 request routing 拆成三個責任。Envoy Endpoint 對外提供 private endpoint，Body-Based Router 讀取 OpenAI-compatible request 的 model 欄位，Endpoint Picker 則用 model-serving pod 的即時 metrics 做選擇。這個設計讓同一個 endpoint 可以服務多個 model pool，也讓 LoRA adapter residency 成為 routing signal。應用程式不需要改用新的 SDK，但平台要管理好 metrics freshness，否則 routing decision 會建立在過期狀態上。

AWS 公布的 benchmark 在 mixed GPU、bursty traffic 與 shared prompt prefix 三種情況測試，結果依模型不同而變化。uniform fleet 與 steady traffic 下，官方表格顯示 routing 差異接近 run-to-run variance，這點比單一的最大改善數字更值得注意。跨 cluster、跨 region、global rate limiting 與 cost-tier-aware traffic shaping仍列為後續方向，現階段的可用範圍是 per-cluster routing。部署前應用同一組 prompt、context length、concurrency 與 GPU mix 重跑測試，再決定是否值得引入新的 addon lifecycle。

### PostgreSQL 19 Beta 4 先收斂功能，再靠測試進入 RC

[PostgreSQL Global Development Group 的公告](https://www.postgresql.org/about/news/postgresql-19-beta-4-released-3386/)指出，Beta 4 撤回 SQL/PGQ、online data checksum toggle、temporal update/delete，以及 ALTER TABLE ... MERGE PARTITIONS 與 SPLIT PARTITIONS 等功能。這些變更不是單純的 bugfix，而是把尚未完成社群 review 的功能移出 PostgreSQL 19。版本也修正 foreign key constraint check、new REPACK command、WAIT FOR、logical replication synchronization 與 autovacuum scoring system 等問題。

Beta 4 仍然不是 production release。[官方 beta 說明](https://www.postgresql.org/developer/beta/)明確提醒，beta 期間功能可能發生不相容變更，並建議平台、driver、tool 與 utility 維護者先測試。專案目前規劃 10 月初進入 release candidate，但 GA 時程仍依測試結果而定。升級測試應使用 major-version migration 流程，常見路徑是 pg_upgrade 或 pg_dump 搭配 pg_restore，不應把 beta binary 直接覆蓋現有資料目錄。

~~~bash
# 先在測試環境確認來源與目標版本
psql --command 'SELECT version();'
pg_dump --format=custom --file=app.dump appdb

# 目標叢集初始化完成後，再還原測試資料
createdb appdb
pg_restore --dbname=appdb app.dump
~~~

### Go 1.27 的 portable SIMD 仍是實驗功能

[Go 團隊的 9 月 24 日文章](https://go.dev/blog/simd-experiment)說明 Go 1.26 先提供 amd64 的 architecture-dependent API，Go 1.27 再加入 arm64 NEON、Wasm 以及平台與 vector size 無關的 simd 介面。[Go 1.27 release notes](https://go.dev/doc/go1.27)則把實驗功能與其他工具鏈變更放在同一個版本脈絡中。portable API 只承諾各平台共同支援的操作，缺少硬體指令的環境會走 emulation，因此同一份程式可以在不同架構執行，但不代表每台機器都有相同吞吐量。

以下程式碼取自 Go 團隊示範的 inner product 形狀。Len() 決定目前實例的 vector width，尾端不足一個完整 vector 的資料則使用 partial load。使用前要以 GOEXPERIMENT=simd 啟用實驗功能，並對 AVX、NEON、Wasm 與 emulation 路徑分開做 benchmark。

~~~go
func innerProduct(x, y []float32) float32 {
    var a simd.Float32s
    var i int
    for i = 0; i < len(x)-a.Len()+1; i += a.Len() {
        u := simd.LoadFloat32s(x[i : i+a.Len()])
        v := simd.LoadFloat32s(y[i : i+a.Len()])
        a = u.MulAdd(v, a)
    }
    if i < len(x) {
        u, _ := simd.LoadFloat32sPart(x[i:])
        v, _ := simd.LoadFloat32sPart(y[i:])
        a = u.MulAdd(v, a)
    }
    return sum(a)
}
~~~

Go 團隊預計在 Go 1.28 擴充 SVE 與更多 mask、reduction、shuffle 操作。這些 API 還在實驗階段，套件設計與支援範圍可能改變，適合先用在可替換的 compute kernel，不適合把整個 production ABI 綁死在目前介面上。

### Kong Operator 2.3 把 AI Gateway 資源納入 GitOps

[Kong Operator 2.3 公告](https://konghq.com/blog/product-releases/kong-operator-2-3)在 9 月 25 日發布，新增 AI Gateway 的 Kubernetes CRD 管理，包含 control plane、provider、model、policy、authentication 與 consumer。官方文件的安裝路徑要求啟用 ENABLE_CONTROLLER_AIGATEWAYDATAPLANE=true，並透過 Konnect credential 建立 control plane 與 data plane。這種設計把 model routing、prompt injection detection、topic allowlisting 與 per-team API key policy 放入可版本控制的 manifest。

~~~yaml
apiVersion: aiconfiguration.konghq.com/v1alpha1
kind: AIGatewayModel
metadata:
  name: gpt-4o-mini
spec:
  aiGatewayRef:
    type: namespacedRef
    namespacedRef:
      name: my-ai-gateway-cp
  apiSpec:
    type: model
    model:
      name: gpt-4o-mini
      formats:
        - type: openai
      capabilities:
        - generate
      config:
        route:
          paths:
            - /v1
      targets:
        - name: gpt-4o-mini
          provider:
            name: openai-provider
          config:
            type: openai
            openai:
              upstreamURL: https://api.openai.com/v1/chat/completions
~~~

2.3 同時加入 TCPRoute、UDPRoute、GRPCRoute 與 AI、Event Gateway dataplane 的 HPA 支援。平台團隊需要把 CRD schema、Konnect API 權限、secret rotation 與 admission webhook 的憑證生命週期放進同一份變更審查。對只需要單一 LLM endpoint 的叢集而言，這套控制面可能比直接使用既有 Ingress 更複雜，價值主要在多 provider、多 team 與 GitOps policy 的一致管理。

### 可觀測性與 agent runtime 開始共享同一套治理問題

OpenTelemetry 在 [Instrumentation Ecosystem Explorer 文章](https://opentelemetry.io/blog/2026/exploring-instrumentation-ecosystem/)中提出，把 component version、configuration、semantic convention 與實際 conformance test 結果放在同一個可比較的資料模型。文章也特別提醒，某個情境沒有觀察到 optional attribute，不等於整個 instrumentation 永遠不會產生它。這種證據分層對 agent runtime 同樣重要，因為「支援某個工具」和「在特定 policy、model、network 與 credential 狀態下真的可用」不是同一件事。

Microsoft 在 [Copilot Managed Runtime 公開預覽](https://www.microsoft.com/en-us/copilot/blog/copilot-studio/build-where-you-want-run-with-confidence-now-microsoft-hosts-and-manages-the-code-created-by-copilot/)中把 tenant boundary、Entra identity、connector policy、Git versioning、inventory 與 lifecycle control 放進託管執行環境。DigitalOcean 在 [Managed Agents 公開預覽](https://www.digitalocean.com/blog/why-we-built-managed-agents)中則以 Firecracker microVM、MCP action gateway、credential brokering 與以 CPU-second 計費的模型組合 agent runtime。兩者的產品定位不同，但共同點是把 agent 的執行環境、工具權限、資料狀態與成本紀錄放進平台層，而不再只交給單一 CLI 或 prompt 管理。採用這類服務前，應要求供應商提供可匯出的 audit event、credential non-disclosure 保證、network egress policy 與刪除或移交 session state 的明確行為。
