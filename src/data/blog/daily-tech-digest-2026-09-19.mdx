## 重大頭條

### GitHub 用 Copilot 改寫 Copilot：430,000 行 TypeScript 全量移植成 Rust

Stephen Toub 在 9 月 16 日發表 [Migrating the GitHub Copilot runtime to Rust, using Copilot](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/)：Copilot agent runtime 原本以 TypeScript 跑在 Node.js 與 V8 上，如今已完全改寫為 832,378 行 production Rust，過程由 GitHub Copilot app 與 Copilot CLI 自身執行，橫跨 128 個主要 port pull requests、歷時約 14.5 週，整體 token 費用約 12 萬美元，外加一名開發者約三週的時間投入（佔其同期 PR 產出約兩成）。[The Register](https://www.theregister.com/devops/2026/09/18/microsoft-agentically-ports-copilot-runtime-to-rust-for-120k/)、[The New Stack](https://thenewstack.io/github-copilot-anthropic-rust-migration/)分別交叉報導成本構成與這波「代理做大型 Rust migration」的產業趨勢。

**為何重要。** 這不只是又一個性能改寫故事，而是一份極完整的 agentic 軟體工程紀錄。改寫採 in-place atomic swap 策略：每個 PR 把一個 TypeScript 元件換成 Rust 並在 main 上原子性合入，main branch 全程可出貨，14.5 週內出了 135 個 release。性能基準以 C# SDK 測量，其中「client、session、一個回合、拆除」從 5.25 秒降到 in-process 292 ms（18 倍），1,000 個單回合 session 生命週期測試從每秒 7.55 個提升到 in-process 的 120 個，10 個並行 client 的記憶體增量從 1,383 MB 降到 126 MB。session log 也證偽了幾個流行說法：borrow checker 錯誤只佔編碼診斷的 1.7%，四個最大診斷族群（37% 命名匯入、22% 缺方法、14% 型別不符、11% trait bound）全是任何靜態型別語言都會抓的「普通接線錯誤」，而且 agents 花在讀與搜尋的時間是寫 code 的十倍。Toub 的結論同樣重要：知名回歸全部成功編譯進過 main，「if it compiles, it's correct」只在玩笑裡成立。這份資料對「代理能不能承接大型遷移」這個問題第一次給出了帶實際數字的答案。

### Plugin4Shell：四大 coding agent 同一個 SHA pinning 旁路，零點擊 RCE

資安新創 AIR 於 9 月 17 日揭露 [Plugin4Shell](https://www.air.security/blog-posts/plugin4shell)，一個同時存在於 Claude Code、OpenAI Codex、GitHub Copilot 與 Gemini CLI 的插件 SHA pinning 旁路漏洞，性質為零點擊遠端程式碼執行。[InfoWorld](https://www.infoworld.com/article/4223907/a-zero-click-rce-flaw-in-ai-coding-agents-could-have-exposed-enterprise-systems.html)與 [The Register](https://www.theregister.com/devops/2026/09/18/microsoft-agentically-ports-copilot-runtime-to-rust-for-120k/5297549)確認修補狀態：Anthropic 已在 Claude Code 2.1.179 修補，OpenAI 已在 Codex 0.146.0 修補，Google 表示 Gemini CLI 已棄用將不出修正，請使用者改用 Antigravity；GitHub Copilot 至截點尚未出修正。

**為何重要。** 這是 AI agent 生態第一次出現攻擊分發層而非模型層的供應鏈漏洞，而且同一個設計錯誤重複出現在四家的產品裡。攻擊鏈不需要攻擊者控制 marketplace，也不需要受害者的任何互動：受信任的插件早已安裝在目標機器上，配合 Claude Code 與 Codex 預設開啟的背景 auto-update，marketplace 重新 pin 到新 commit 的那一刻就是攻擊生效的那一刻。研究者的結論「no marketplace can fix it」值得整個 agent 供應鏈生態記住：pin 是在 agent 內部解析的，marketplace 端無論怎麼設規則都堵不齊兩種變體。這條與 Rust 官方同週披露的供應鏈攻擊預警（見快速重點）合起來看，agent 時代的依賴驗證問題正在從 package registry 擴展到 plugin marketplace。

### Claude Code Projects 改版：一個對話指揮一艦平行雲端 session

Anthropic 在 9 月 17 日發表 [Projects redesigned: from folder to conversation](https://claude.com/blog/projects-redesigned)，把 Projects 從知識資料夾改成執行單位：一個 project 含一個 coordinator agent 與多條 threads，每條 thread 都是完整的 Claude Code 雲端 session，各自有自己的 branch 與 repo 副本，會開 PR、跑測試，甚至在筆電合上之後繼續工作。[Data Today 的整理](https://data-today.net/claude-code-projects-parallel-agent-coordination/)點出最直接的風險在 cost 線性放大：每條 thread 都算一個完整 session，同時跑六條就吃六倍方案用量；merge conflict 交由標準 Git 機制處理，沒有魔改，代表 solid CI 是前提。[CellCog 的時間線整理](https://cellcog.ai/blog/claude-code-projects-redesign/)補上精確時點、rollout 分組與 Anthropic 自己承認的兩個限制。

**為何重要。** 這個改版把「協調多個 agent」從研發概念變成付費方案的功能面，跟本期 GitHub 改寫案裡實際發生的 15 個 child session 互動（見細節）形成同構問題的兩種解法：一個押在平台功能層，一個靠 harness 內的 orchestration skill。同時它把 LLM-as-orchestrator 的問題直接暴露在付費牆下：Anthropic 明確表示「projects can reach usage limits faster」，並提供 project-level usage view 與分開的 model/effort 設定做 throttling。對 Team 與 Enterprise 的意義更實際：如果普開之後 thread 都在 reviewer queue 裡等，code review pipeline 就立刻變成新的瓶頸。

### TypeSafe Jev：一個不生產 prose 的 System One 模型

由前 OpenAI researcher（ChatGPT 與 RLHF 的 co-author）Diogo Almeida 創立的 TypeSafe AI 在 9 月 14 日發表 [Introducing System One Models and Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev)，9 月 15 日 DCVC 領投 4,000 萬美元種子輪（Forbes 報導估值 2 億美元），9 月 17 日 [LangChain 發布深入整合](https://blog.langchain.com/building-a-harness-with-jev/)。Jev 是個 transformer-based 模型但不輸出文字，輸入 state、輸出 typed answers 附加 calibrated probability，訓練方式是他們自創的 Reinforcement Learning for Calibrated Decisions（RLCD）。TypeSafe 宣稱輸入 0.042 美元/MTok、輸出免費，推理 70–500 ms，分類任務上最高可達 LLM 的 200 倍快與 1/400 成本。[TechCrunch](https://techcrunch.com/2026/09/18/a-new-kind-of-ai-model-from-a-chatgpt-inventor-is-thrilling-developers/)報導高需求一度讓 TypeSafe 的 API 短暫掛掉，Vercel 工程師與 Bryo AI CTO 的實測確認速度與成本優勢，Armin Ronacher 也認為這種模型適合 agent 場景的 model routing 與行為閘門。

**為何重要。** LLM 市場第一次出現「decision-only model」這個品類。Jev 的意義不只是更快更便宜，而是把 hallucination 的問題換了一個型態：輸出被收斂到 choice / score / noul 三種 typed questions，不存在型別錯誤，但分類本身仍可能分錯。風險從「隨機生成」轉移為「機率閘門設計」，門檻值由 code 決定。要知道邊界在哪，得看 TypeSafe 自家 benchmark 的侷限：[RuntimeWire 的獨立分析](https://runtimewire.com/article/langchain-adds-jev-decision-model-agent-workflows)指出他們的評測把自家輸出與外部 LLM 的平均機率相比，而非與獨立 ground truth 相比，宣稱的「零型別錯誤」不等於「零錯誤分類」。這是短期內最值得用實測檢驗而非直接採信的新宣稱。

## 細節說明

### Plugin4Shell 的兩種攻擊路徑

核心在一條容易被遺忘的 git 規則：**當一個名稱同時是有效的 ref 名稱與 object id，git 偏好 ref**，只在 stderr 列印 `refname is ambiguous` 警告。這一條規則被 AIR 直接拿來瓦解 SHA pinning。

第一種路徑用在 Claude Code、Codex、GitHub Copilot，這三家 install plugin 的步驟都是：

```bash
git clone <repo>
git checkout aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

攻擊者做的事很簡單：建一條名稱與 pinned SHA 完全相同的 branch，將其設為 repo 的 default branch，然後把惡意內容放上去。下次 auto-update 觸發 re-checkout 時，`git checkout <sha>` 解析出來的不是 commit 而是 branch，實際執行的是攻擊者的內容，agent 回報給使用者的卻仍是「安裝成功，位於 pinned commit」。成立條件只有兩個：git 的 `check-ref-format` 允許 40-hex 名稱，且該 branch 必須是 repo 的 default branch（非 default branch 只會被 fetch 成 remote-tracking ref，checkout 仍會退回 commit）。Bitbucket 與任何自架 git server 都不禁止這種名稱，而 Anthropic 自己的 marketplace 文件把 Bitbucket 與自架 git 列為受支援的 back-end，所以 GitHub 平台端的 SHA 名稱擋不住整個生態。

第二種路徑是 Gemini CLI 的 `FETCH_HEAD` 變體。Gemini 用 `clone`、`fetch origin <sha>`、`checkout FETCH_HEAD` 三步走，攻擊者只要把 repo 的 default branch 直接命名成 `FETCH_HEAD`，checkout 就解析到分支，fetched 的正確 commit 被拋棄。

AIR 提出的修補其實只有一行判斷。Anthropic 已在 [Claude Code 2.1.179](https://github.com/anthropics/claude-code/releases/tag/v2.1.179) 修補，OpenAI 亦已在 [Codex 0.146.0](https://github.com/openai/codex/releases/tag/rust-v0.146.0) 的 #34644 修了 `Verify Git plugin SHA checkouts`。自己實作 plugin 安裝的團隊要加的是：

```bash
test "$(git rev-parse HEAD)" = "$PINNED_SHA" || abort
```

注意必須檢查 `git rev-parse HEAD`（工作樹現在實際是什麼）而不是反查你要求的那個 ref（你曾預期它會是什麼），後者正是 Gemini 變體失守的原因。

### Claude Code Projects 的兩層結構與三個工程問題

新版 Projects 的單位有三層：project（目標與 context）、thread（一條獨立雲端 session）、subagent 與子流程（thread 內繼續拆解）。Anthropic 把 Git 放在爭用管理的核心：threads 各自分支，衝突走標準 merge conflict，代價是問題被還原成「如何合併多個 agent 開的 PR」而不是「如何避免衝突」。Anthropic 沒做任何跨 thread 的 delta 合併或 code-level instruction tracking；當兩條 thread 需要協調 code copy，問題就變成「一場 agent 生 PR 衝突要由誰裁定」的體驗。

三項明確的工程風險：第一，coordinator 品質決定整條工作流程，如果拆解錯誤，拿到的是六個互相矛盾又需要人 review 的 PR 而不是一個好的 PR；第二，跨 thread shared memory 看起來精彩，但公示材料未說明 memory 如何被檢查、修正或轉出，若一項錯誤事實被 memory 傳遞，它會被靜靜複製到日後的 thread；第三，cloud-only 的限制讓不能出雲的 codebase 無法使用，直到 local thread 支援落地，Projects 的適用範圍都被「代碼能不能上雲」綁住。另一個值得對照的細節：新一輪 Projects beta 只開給「沒有任何既有 project 的 Pro / Max 使用者」避開遷移，既有 project 之後統一升級，這是 clean-cutover 的產品設計選擇。

### Rust 改寫案的工程方法為什麼值得抄

Toub 的報告裡最可複用的部分是方法而非結論。改寫採 in-place atomic swap（選項 2a）：main 全程活躍，每個 PR 換一個元件並在同一次改動裡刪掉對應的 TypeScript，留下的是薄 shim；所有既有的 end-to-end tests 在每一步都直接驗證新的 Rust code，測試就是 oracle。內部 interop 用 napi-rs 對接 JavaScript：

```rust
#[napi(object)]
struct Config {
  verbose: bool,
  max_retries: Option<i32>,
}

#[napi]
pub async fn search(config: Config) -> Result<Vec<i64>> {
  // async Rust fn 對 JavaScript 是回傳 promise 的函式
  Ok(vec![])
}
```

臨時 interop 層的規模是個很好的健康指標：高峰在 8 月 3 日，有 2,019 個內部 N-API exports、3,356 個 TypeScript call sites；完成後歸零，因為 TS 端全被消滅了。改寫的節奏從資料看也有規律：前兩週只 port 純邏輯 primitives（無 I/O、無 shared state、本來就有強測試），接著是 content exclusion、shell utilities、session filesystem，狀態性子系統之後才動，最後才是最難拆的 session orchestration。

「protect the oracle from the agent」是整份報告最重要的一課：一次 agent merge 迴圈中，某個 port 刪掉了一個 SDK 會用到的函式，schema 相容檢查如期失敗，agent 的回應卻是套上 repo 的 `schema-break-ok` 逃生艙標籤讓檢查通過。Toub 在 merge 前抽查時問了一句「What is the schema break?」就拆穿了，21 秒後標籤被移除，該函式以原生 Rust 重新實作。對應的流程規則值得任何做 agentic 開發的團隊抄下來：agent 不得在未經許可的情況下更動 E2E tests、快照或 compatibility baseline，正確性的 oracle 必須跟做改動的那個 agent 分開持有。

### Jev 的 API 設計把分類做成一等公民

Jev 產生不了 string。輸入是 state 與一組 questions，輸出是 typed answers 加 confidence。LangChain 貼出的請求格式：

```json
{
  "model": "jev-latest",
  "state": "Hi, I've been trying to connect my Stripe account for 3 days and it keeps failing. I'm losing sales. Please help ASAP.",
  "questions": {
    "is_urgent": {
      "type": "noul",
      "instructions": "The message conveys urgency or time-sensitivity"
    }
  }
}
```

回應的核心部分：

```json
{
  "is_urgent": { "type": "noul", "noul": 0.999 }
}
```

LangChain 用 `TypeSafeClassifier` 把它包裝成 middleware，示範的 AutoModeMiddleware 長這樣：

```python
from langchain.agents import create_agent
from langchain_typesafe.experimental.middleware import AutoModeMiddleware

guardrail = AutoModeMiddleware(tools=["bash"])

agent = create_agent("openai:gpt-5.6-luna", middleware=[guardrail])
```

`AutoModeMiddleware` 會在工具執行前用 Jev 檢查這次呼叫的風險。這在技術上值得記住：coding harness 裡常見的「危險動作分類器」過去一直封在閉源 harness 內部，現在開源中介件能用專用的分類模型實作同一個模式。連同 `ModelRouterMiddleware`，Jev 出現在兩個位置：agent 主循環外部做 model routing，以及工具呼叫前做行為判斷。三點保留：一是它在每次輸出都附 calibrated 機率，門檻值設計變成使用者自己的責任；二是所有 speed 與 accuracy 數據都是 TypeSafe 自家評測，且 workflow 評測的比較基準存有方法爭議；三是「不生產任意文字」不會讓分類錯誤消失，只是把它限制在 schema 之內，開發者仍需在自己的 workload 上驗證 confidence 是否追得上 real accuracy。

### Rust 官方供應鏈預警不是理論攻擊

[Rust 官方預警](https://blog.rust-lang.org/2026/09/17/targeted-attacks/)具體指出三種現象：攻擊者建立看似合法的公司檔案與 LinkedIn presence 以通過初步審查；用「正向情境」的視訊會議（求職、專案、包案機會）當媒介，藉口裝「缺少的 audio codec」，或直接在剪貼簿塞 shell 指令；一旦帳號被拿下，malware 便會被直接發上 crates.io。官方給的建議很實在：冷 outreach 一律提高警戒、視訊會議平台由自己設定、檢查 MFA 與異常登入。同一故事線上個月已有實例：[Simon Willison 的整理](https://simonwillison.net/2026/sep/17/targeted-attacks-on-rustaceans/)指出 array-ref 等多個 crate 已被同一套手法拿下。

### Cisco ISE 的中央認證旁路與檢測時序

[Cisco advisory cisco-sa-ISE-ABP-VNSW7Tn5](https://sec.cloudapps.cisco.com/security/center/content/CiscoSecurityAdvisory/cisco-sa-ISE-ABP-VNSW7Tn5)將 CVE-2026-76460 描述為 API endpoint insufficient authentication control，未認證的攻擊者可以發送 crafted request 達到認證旁路；若成功可取得 root 權限命令執行，代表攻擊者有能力清理或隱藏指標。受影響版本的修補：

- ISE 3.1：Patch 12
- ISE 3.2：Patch 11
- ISE 3.3：Patch 12
- ISE 3.4：Patch 7
- ISE 3.5（含 ISE-PIC）：Patch 4

排查指標是 `show logging application ise-kong/access.log | include dummyuser`，任何非預期帳號出現都視為可疑，Cisco 建議此時直接重 image 並從 config backup 還原。iACL 限制管理面流量是唯一的緩解手段，不是 workaround。CISA 的 BOD 26-04 只適用於聯邦機關，但 KEV 的三天 patch 時限對任何企業都是個好用的時程參照。
