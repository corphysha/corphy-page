## 重大頭條

### Pando 保留 Git，用分支層級協調與共用 packfile 擴充吞吐量

[OpenAI 於 11 月 2 日公開 Pando 架構](https://openai.com/index/scaling-git-at-openai/)，這是其 monorepo 的 Git 後端，不是新的版本控制客戶端。官方表示正式環境的 push 延遲中位數降低近 80%，每天傳送接近一個 petabyte 的 Git 資料。[The New Stack](https://thenewstack.io/openai-pando-git-backend/)與 [MarkTechPost](https://www.marktechpost.com/2026/11/02/openai-pando-git-backend-monorepo/)均說明其核心取捨：不同分支不再共用全域更新順序，讀取端則下載可重用的 packfile。

為何重要：大量 agent 分頭寫入時，增加機器不會自動消除共用協調點。Pando 把協調限制在個別 ref，並把讀取工作從逐客戶端計算差異，改成傳送已存在的不可變資料。代價是跨分支讀取不能假設來自同一時間點，以及可能傳送客戶端已持有的物件。

### Claude message threads 公開測試，縮小請求但不縮短模型上下文

[Anthropic 的 message threads 公告](https://claude.com/resources/articles/message-threads)讓 Messages API 在第一輪收到完整對話後，後續只接收新增訊息與前一個回應的識別碼。依[官方 release notes](https://platform.claude.com/docs/en/release-notes/overview)，功能於 11 月 2 日進入 beta。[The New Stack](https://thenewstack.io/anthropic-claude-message-threads/)與 [The Next Web](https://thenextweb.com/news/anthropic-message-threads-beta-claude-api-agents)都指出，這不會直接減少 token 帳單。

為何重要：長對話的上傳與請求處理，也可能是 agent 延遲來源。官方聲稱對 500k 至 1M token 的 Claude Code 請求，首個 token 時間中位數降低約 35%。這個數字有特定上下文長度與產品工作負載，不能套用到所有 API 呼叫，更不能解讀為整體任務快了 35%。

## 快速重點

以下是兩則事件的不同技術面向，不另計為獨立新聞。

- [Pando](https://openai.com/index/scaling-git-at-openai/)對個別 ref 提供可序列化更新，跨 ref 則不保證全域時間點快照。
- [Pando 的讀取路徑](https://openai.com/index/scaling-git-at-openai/)使用 Git 的 `packfile-uri` 傳回下載位置，Express 區域快取負責傳送資料。
- [MarkTechPost](https://www.marktechpost.com/2026/11/02/openai-pando-git-backend-monorepo/)明確將效能數字列為 OpenAI 自述，而非獨立 benchmark。
- [Message threads](https://claude.com/resources/articles/message-threads)閒置五分鐘後到期，客戶端必須能重送完整歷史。
- [Anthropic release notes](https://platform.claude.com/docs/en/release-notes/overview)區分五分鐘有效期限與最後使用後最遲一小時內刪除，兩者不是同一承諾。
- [The New Stack](https://thenewstack.io/anthropic-claude-message-threads/)指出 threads 可與 prompt caching 搭配；減少上傳與折扣計費是不同機制。

## 細節說明

### Pando 的一致性保證止於何處

Pando 接收 push 時，先驗證並將 packfile 串流寫入 blob storage，不必在伺服器建立完整的本機 repository。metadata store 記錄新的 ref version、對應 pack 與依賴的早期版本，再更新 ref 指標。依[官方架構說明](https://openai.com/index/scaling-git-at-openai/)，單次寫入的 metadata 讀寫為 O(1)，但這不表示 pack 的資料驗證或傳輸成本也是常數。同一分支的競爭仍需協調，不同分支才可獨立前進。讀取某個版本時，系統提供產生該版本所需的因果歷史，因此不是任意缺漏物件的最終一致讀取。

以下 JSON 是依官方 foo/bar 情境改寫的教學資料，不是 Pando API。兩個讀取者可能取得不同的跨分支組合；不能只憑分支名稱建立可重現的建置輸入。

```json
{
  "readerA": { "foo": "version-1", "bar": "version-2" },
  "readerB": { "foo": "version-2", "bar": "version-1" }
}
```

若產品需要多個元件共同發布，較穩妥的工程設計是另外保存一份不可變的 release manifest，指定每個元件的 commit ID。這是本文的設計建議，不是官方新增功能。manifest 本身也必須經過審核並固定版本，否則只會把同一個競爭問題移到另一個檔案。以下結構刻意將可移動分支與固定 revision 分開。

```typescript
type ReleaseInput = {
  component: string;
  repository: string;
  commit: string; // 實際紀錄填入完整 commit object ID，不填分支名稱
};

type ReleaseManifest = {
  release: string;
  inputs: ReleaseInput[];
};
```

### 為什麼多傳一些物件，反而可能更快

傳統 fetch 可針對每個客戶端已有的物件產生差異 pack，節省傳輸量，但也要支付計算與 I/O 成本。Pando 選擇重用已上傳的 packs，讓多個讀取者下載相同位元組。這有利於區域快取，卻不保證每個客戶端都收到最小資料量。[官方報告](https://openai.com/index/scaling-git-at-openai/)指出曾在一小時內傳送超過 57 TB packs，其中超過 99% 位元組來自本機磁碟快取。這是特定內部系統的觀測值，不是任意 Git 伺服器採用快取後都能達成的結果。

每次 push 產生的小型 L0 pack 若一直累積，fetch 就得處理大量小檔。Pando 在背景將 packs 組成幾何級數大小的 covers，概念接近 LSM-tree compaction。covers 同時支援更有效率的下載與版本搜尋，官方以 O(log Δ) 描述 fetch planning 的 metadata 讀取，Δ 是待跨越的 ref-version 距離。這不應改寫成整個 fetch 的網路時間是對數成長。對實際營運而言，應分開量測 negotiation、pack 選擇、下載與 indexing，才知道瓶頸是否真的移除了。

### Message threads 改的是請求傳輸，不是 token 計算方式

以往每一輪 Messages API 呼叫都重送歷史訊息，長工作階段會重複傳送大量相同內容。threads 把先前對話暫留在伺服器，下一輪帶上前一回應 ID 與新訊息即可。模型仍看到完整對話，因此不能用 HTTP body 大小推算模型輸入 token。[官方公告](https://claude.com/resources/articles/message-threads)明言 token usage 不變，標準費率與既有 rate limits 仍適用。把它當成壓縮上下文或新的成本折扣，會誤判預算。

以下 Python 範例依 [The New Stack 的參數說明](https://thenewstack.io/anthropic-claude-message-threads/)整理，展示 create 與 continue。模型名稱由環境變數提供，實際部署需選擇帳戶支援的模型與含此 beta 欄位的 SDK。範例未執行付費 API 呼叫，也未涵蓋 streaming、工具回合與錯誤復原。

```python
import os
import anthropic

client = anthropic.Anthropic()
options = {
    "model": os.environ["CLAUDE_MODEL"],
    "max_tokens": 256,
    "betas": ["message-threads-2026-08-12"],
}

first = client.beta.messages.create(
    **options,
    thread={"type": "create"},
    messages=[{"role": "user", "content": "Explain Git packfiles briefly."}],
)

second = client.beta.messages.create(
    **options,
    thread={"type": "continue", "previous_message_id": first.id},
    messages=[{"role": "user", "content": "How do reusable packs help caches?"}],
)

print(second.id)
```

沒有 threads 時，第二輪需帶上第一輪 user 訊息、assistant 回應與新增 user 訊息。上例的第二輪只傳新增訊息，先前內容由 thread 接回。應用程式仍需保存自己的完整歷史，不能把短期 thread ID 當成資料庫主鍵或永久對話儲存。對含敏感資料的流程，還要確認平台的保留與合規條件，不能從「記憶體中加密」推導成適用所有零保留政策。

### 五分鐘期限會影響工具工作流程

五分鐘對互動式文字回合可能足夠，對編譯、大型測試與人工核准卻不一定。若工具完成前 thread 已過期，客戶端需要從本機歷史重新建立 thread，而不是遺失前文。[官方 release notes](https://platform.claude.com/docs/en/release-notes/overview)另註明最後使用後最遲一小時內刪除，這是資料生命週期資訊，不是五分鐘內一定會清除的保證。工程監控至少要區分成功續接、到期重建與一般請求失敗。只有觀察到期比例與延遲分布，才能評估這項 beta 對自己的 workload 是否有幫助。

Pando 與 threads 都藉由重用既有資料減少重複工作，但可接受的語義不同。Git 場景放寬跨分支快照保證，API 場景引入有期限的伺服器狀態。兩者都沒有讓驗證工作消失。前者仍需測試 ref 更新與物件依賴，後者仍需處理完整歷史保存與續接失敗。效能改善應連同這些條件評估，不能只比較公告中的百分比。

## 值得追蹤的版本、RFC 與提案

- [Message threads beta](https://platform.claude.com/docs/en/release-notes/overview)使用 `message-threads-2026-08-12` 標記。後續應追蹤 SDK 支援、到期錯誤處理與正式版政策，不把 beta header 日期誤認為公開發布日期。
- [Pando 的 Git 貢獻](https://openai.com/index/scaling-git-at-openai/)包含 pack 下載、中斷恢復與追蹤改善。官方區分已進 upstream 的變更與仍在其公開 Git build 的功能，不能將 parallel indexing 或 explicit haves 全部宣稱為已進入某一穩定版。
