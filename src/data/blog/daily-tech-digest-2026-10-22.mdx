## 重大頭條

### PHP 修補兩項可導致未授權遠端程式碼執行的核心漏洞

PHP 團隊在 10 月 21 日提前發布安全更新，修補 **CVE-2026-109618** 與 **CVE-2026-109619**，兩者 CVSS v4.0 均為 9.2。固定版本為 PHP **8.5.12、8.4.27、8.3.36 與 8.2.35**；PHP 官方指出，所有對外提供 Web 請求的安裝都應立即更新，包含 PHP-FPM、Apache mod_php、php-cgi、FrankenPHP 與 LiteSpeed。[PHP 官方公告](https://www.php.net/archive/2026.php)、[PHP Foundation 技術說明](https://thephp.foundation/blog/2026/10/21/todays-php-security-release-and-how-were-strengthening-php-security/)、[Ars Technica 報導](https://arstechnica.com/security/2026/10/php-maintainers-tell-web-devs-to-prepare-themselves-for-critical-security-patches/)與 [TechTarget 報導](https://www.techtarget.com/cybersecurity/news/366652444/PHP2Shell-22M-exposed-servers-at-risk-as-emergency-patches-released/)交叉確認漏洞影響與更新時程。

第一項漏洞涉及記憶體耗盡時的錯誤處理：PHP 可能留下未完整初始化的 request 狀態，後續清理流程卻把它當成有效資料。第二項漏洞則是 fatal error 路徑留下指向已釋放記憶體的全域狀態，之後由同一 worker 處理的請求可能使用該記憶體。PHP Foundation 表示，兩項問題都觸及每個請求常走的記憶體管理與錯誤處理路徑；Apache mod_php 已展示可在應用程式程式碼執行前觸發的 RCE，PHP-FPM 也在應用程式路徑確認 RCE。

為何重要：更新不能只靠掃描應用程式的 Composer 依賴，PHP runtime 可能藏在容器基底映像、主機套件、託管平台或第三方產品中。PHP 官方表示沒有完整替代緩解措施，設定調整只能降低特定觸發路徑的風險。盤點所有 PHP 執行環境、更新後重建容器並檢查修補前的可疑活動，應視為同一項事件處理，而非只把版本號改掉。

### GitHub 預覽 npm 套件防火牆，將安裝政策放到 registry 請求路徑

GitHub 於 10 月 20 日為 GitHub Enterprise Cloud 推出 Package Firewall 公開預覽。管理員可設定套件最低發布天數、惡意程式與漏洞公告攔截、attestation 降級檢查，以及新加入 install script 的檢查；開發者工作站、CI runner 與 coding agent 必須改由防火牆 URL 取得 npm metadata 和套件，政策才會生效。[GitHub Changelog](https://github.blog/changelog/2026-10-20-github-package-firewall-in-public-preview/)、[GitHub 設定文件](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/protecting-endpoints-with-package-firewall)與 [DevOps.com 分析](https://devops.com/github-puts-a-firewall-between-npm-and-your-ci-runners/)均描述了這套請求代理與政策控制。

預設值包含一日最低套件年齡、阻擋已知惡意套件、attestation 降級與新 install script；漏洞公告預設只阻擋 Critical。新套件等待期可設為 1 到 365 天，也能關閉。這類控制針對安裝當下的供應鏈風險，特別是自動化代理或 CI 在無人逐次檢查時安裝依賴的情境。現階段僅支援 npm，預覽期免費，正式推出後預計依用量計費。

為何重要：這是把「依賴版本是否可下載」變成組織層的政策決策，而不是要求每個專案自行維護一份安全設定。不過，防火牆只檢查經過它的流量，若另一個 registry、快取或安裝步驟能繞過代理，政策就不完整。套件新鮮度限制也有取捨，急需的安全修補可能被冷卻期擋住，因此例外審核和完整的 registry 路由盤點同樣重要。

### TorchNeuron 將 Trainium 接入 PyTorch 原生裝置介面

AWS Neuron 2.33 在 10 月 21 日將 TorchNeuron 列為公開 Beta。這個原生 PyTorch backend 透過 PyTorch 的 PrivateUse1 擴充點註冊 `neuron` 裝置，支援 Trainium2 與 Trainium3 的 eager execution、`torch.compile`、分散式訓練與 Neuron Kernel Interface。PyTorch 部落格說明了設計與測試範圍，Hugging Face 說明 Transformers、Diffusers、Accelerate、PEFT、TRL 等工具的整合，AWS 發布說明則確認 Neuron 2.33 的功能已可使用。[PyTorch 技術文章](https://pytorch.org/blog/introducing-torchneuron-native-pytorch-backend-for-aws-trainium/)、[Hugging Face 整合說明](https://huggingface.co/blog/hf-torchneuron)、[AWS Neuron 2.33 發布說明](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-announce-neuron-2-33-0/)與 [TorchNeuron 程式庫](https://github.com/aws-neuron/torch-neuronx)提供了實作細節。

Hugging Face 指出，前 100 個最常用文字生成模型架構中，TorchNeuron 開箱支援 89%，Optimum Neuron v0.4.5 則為 46%。同一篇文章提醒，static shapes 和編譯圖重用仍影響實際工作流程；某些模型或運算子仍未支援。PyTorch 團隊公布的測試也列出尚未支援或刻意略過的功能，包括 sparse tensor、forward-mode autograd、部分動態形狀與部分 attention mask。

為何重要：新後端降低了將既有 PyTorch 模型移到 Trainium 時的 API 改寫成本，但不等於 GPU 工作負載可以不測試就直接搬移。團隊仍須量測編譯時間、形狀變化、運算子 fallback、分散式配置和實際吞吐量。這是降低硬體切換摩擦的工程進展，Beta 的模型覆蓋與效能則仍需用真實 workload 驗證。

以下是 Hugging Face 文件中的推論載入方式，重點是以 `device_map="neuron"` 指定裝置，並使用 static cache 限制生成時的形狀變化：

```python
import torch
import torch_neuronx  # 註冊 Neuron 裝置
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "Qwen/Qwen3.8-27B"

tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    dtype=torch.bfloat16,
    device_map="neuron",
).eval()

inputs = tokenizer("The future of AI is", return_tensors="pt")
with torch.no_grad():
    output = model.generate(
        **inputs,
        max_new_tokens=128,
        use_cache=True,
        cache_implementation="static",
    )

print(tokenizer.decode(output[0], skip_special_tokens=True))
```

此範例展示介面，不保證任意模型都能在所有 Trainium 執行個體上直接執行。實際使用前應依模型文件確認支援狀態、Neuron SDK 版本、靜態快取長度與輸入形狀；多核心部署還需明確設定 tensor parallel 或 FSDP。

## 細節說明

### PHP 漏洞排查與更新

兩個 CVE 都不是一般 PHP 應用程式層的輸入驗證問題，而是 runtime 在例外與記憶體生命週期交界處處理不當。CVE-2026-109618 的觸發點與 memory_limit 耗盡時留下的部分初始化狀態有關；CVE-2026-109619 則可能讓前一個請求的狀態指向已釋放記憶體。因 worker 可能重複處理多個請求，後一個請求也可能碰到前一個請求留下的狀態。PHP 官方建議立即更新，且明確指出暫時設定不是完整修補。PHP 8.1 及舊分支已停止上游維護，應確認作業系統供應商是否提供 backport，不能只以版本號較舊就認定沒有修補。

先盤點 runtime，再確認容器與主機實際執行版本：

```bash
# 主機或容器內確認 CLI 版本
php -v

# Debian / Ubuntu 套件環境可列出已安裝 PHP 套件
dpkg-query -W 'php*' 2>/dev/null

# 更新後重建映像並檢查執行中的容器版本
docker compose build --pull
docker compose exec app php -v
```

CLI 與 Web SAPI 可能使用不同 PHP binary，因此還要從 FPM pool、Apache module、容器映像標籤和託管商控制台核對實際服務版本。修補後保留 10 月 20 日起的存取與系統紀錄，再檢查異常子程序、可疑檔案變更和不尋常出站連線。更新只能封住已知漏洞，不能移除更新前可能植入的持久化程式。

### 套件防火牆的政策邊界

Package Firewall 在 npm client 與上游 registry 之間攔截 metadata 和 tarball 請求。管理者先在 enterprise policy 設定規則，再將 endpoint 的 npm registry 指向專屬 URL。GitHub 文件說明，最低套件年齡預設為一天；惡意套件、attestation 降級及新 install script 檢查預設開啟；漏洞公告預設只阻擋 Critical。這些預設值要先與組織的修補時限對照，例如一日 cooldown 可能延後取得剛發布的安全修補。被擋下的套件可以走例外申請流程，但長期例外應設定到單一版本，而非不必要地放寬整個套件範圍。

npm 可在使用者層級的 `.npmrc` 指向企業 URL，token 應放在 CI secret，不應提交到 repo：

```text
registry=https://package-firewall.githubapp.com/npm/enterprises/ENTERPRISE
//package-firewall.githubapp.com/npm/enterprises/ENTERPRISE/:_authToken=${GITHUB_TOKEN}
```

這個設定只適用於 GitHub Enterprise Cloud 的預覽服務。導入時要檢查 npm、Artifactory、CI 快取及 coding agent 的設定，確認沒有另一條路徑直接連到 public registry。對 pnpm、Yarn、Bun 等其他工具，須先確認其 registry 行為和目前預覽支援範圍，不應把 npm 支援誤認為所有 JavaScript 套件管理器都已受保護。

### TorchNeuron 的相容性與效能驗證

TorchNeuron 將 Trainium 表示為 PyTorch 的 `neuron` 裝置，讓模型程式碼透過標準 PyTorch API 執行。這減少了過去以 PyTorch XLA 與 Optimum Neuron 對接時，對 lazy tensor、靜態形狀和專用 trainer 的依賴。Hugging Face 表示其 Transformers 推論整合涵蓋 100 個常用文字生成架構中的 89 個，並建議以 `device_map="neuron"` 載入。這個數字是廠商公布的架構覆蓋結果，不是所有模型的準確率或效能 benchmark。TorchNeuron Beta 仍有未支援的運算子和功能，且編譯器對形狀變動敏感。移植前應以實際 prompt 長度、batch size、cache 設定與分散式配置做測試，並比較輸出正確性、compile time、吞吐量和記憶體使用。
