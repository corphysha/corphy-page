### 2. Cloudflare 最佳化 1.1.1.1 DNS 快取，省下 100TB 記憶體

Cloudflare 於 8/27 發表技術文章，詳述對 1.1.1.1 背後的 DNS 平台「Big Pineapple」做的五項 Rust 記憶體最佳化。每筆快取條目的佔用從 953 bytes 降到 420 bytes（-56%），全 fleet 合計釋放約 100TB 記憶體，相當於 130 台 Gen 13 伺服器的 RAM。同時快取寫入吞吐量提升 43%（62.5 萬 → 89.3 萬 entries/s），查詢延遲下降 19%（828ns → 670ns）。省空間的同時還變快了。

為何重要：這是一篇教科書等級的「資料結構決定系統成本」案例。Big Pineapple 隨時維持 2,500 億筆 DNS 快取條目，每筆省 1 byte 就是全 fleet 250GB。五項最佳化包括 `Vec`/`String` 改 `Box<[T]>`、三個 section 合併為單一 buffer 加 u16 offset、Rust enum 對大 variant 改 boxing、記錄資料改 raw wire-format bytes 存放等，每一步都附 benchmark 與 trade-off 分析（例如 NAPTR 反而變貴，但因罕見所以值得）。

來源：[Cloudflare Blog 原文](https://blog.cloudflare.com/how-we-saved-100-terabytes-of-memory-in-dns-infrastructure/)（8/27）、[GIGAZINE 報導](https://gigazine.net/gsc_news/en/20260828-cloudflare-dns-memory/)（8/28）。

### 3. mklinux v7.0-mk2 公開：一台機器裸機同時跑多個 Linux kernel

Multikernel Technologies 的 Cong Wang 於 8/25 在 Linux Kernel Mailing List 宣布 mklinux v7.0-mk2，這是多核心（multikernel）Linux 樹的首次公開發布。它讓一台實體機器在沒有 hypervisor 的情況下同時執行多個獨立的 Linux kernel：host kernel 擁有 CPU、記憶體與 PCI 裝置池，透過 `kexec_file_load()` 把 spawn kernel 直接開進每個分割的硬體實例。程式碼在 [github.com/multikernel/linux](https://github.com/multikernel/linux)，tag 為 `v7.0-mk2`，基於 Linux 7.0。

為何重要：與 VM 相比沒有 VM exit、沒有第二層分頁表、沒有裝置模型；與容器相比實例不共享 kernel，一個 kernel 的 panic 或漏洞無法波及另一個。實測在 dual-socket Xeon Gold 5418Y 上，檔案系統密集型工作負載（unlink、rename、stat、open）拆成兩個 kernel 後接近 2 倍線性擴展。目前僅支援 x86_64，尚未進入 mainline。把 kernel 視為可排程資源，這個架構實驗值得長期追蹤。

來源：[LKML 官方公告](https://lists.openwall.net/linux-kernel/2026/08/25/1911)（8/25）、[LWN](https://lwn.net/Articles/1090582/)（8/26）、[Phoronix](https://www.phoronix.com/news/Linux-7.0-mk2-Multikernel)（8/26，含 vs KVM benchmark 圖）、[It's FOSS](https://itsfoss.com/news/multikernel-public-release/)（8/27）、[Linuxiac](https://linuxiac.com/multikernel-linux-releases-first-public-kernel-tree-based-on-linux-7-0/)。

### 4. VS Code 1.135 推出 Agent Host Protocol：AI agent session 與編輯器視窗解耦

Microsoft 於 8/26 發布 VS Code 1.135，正式將 Agent Host 架構開放。agent session 改為在獨立程序（Agent Host）中執行，透過開放的 Agent Host Protocol（AHP，MIT 授權）與多個 client 溝通。Session 不再屬於任何視窗：關掉編輯器 session 繼續跑，多個視窗可以連到同一個 session，也支援遠端 host（SSH 或 dev tunnel）。Sessions 面板還能直接接續來自 Copilot CLI、Claude Code、Codex 等外部工具的 session。[協議規範與 client libraries](https://microsoft.github.io/agent-host-protocol/) 已公開，涵蓋 Rust、TypeScript、Kotlin、Go、Swift。

為何重要：byteiota 的分析點出關鍵：這是 2016 年 LSP 的架構重演。LSP 讓編輯器共享語言伺服器，AHP 讓編輯器共享 AI agent。當 session 可攜且 agent-agnostic，編輯器從 session 的擁有者降級為 session 的 client，這直接侵蝕 Cursor 等編輯器 fork 以「原生 AI session」為賣點的優勢。AHP 1.0 尚未定案，現階段適合實驗而非上線依賴。

來源：[VS Code 1.135 release notes](https://code.visualstudio.com/updates/v1_135)（8/26）、[Agent Host 架構官方文章](https://code.visualstudio.com/blogs/2026/08/26/agent-host-architecture)（8/26）、[byteiota 分析](https://byteiota.com/vs-code-1-135-agent-host-protocol-ships-sessions-go-portable/)（8/26）、[Visual Studio Magazine](https://visualstudiomagazine.com/articles/2026/08/26/microsoft-formalizes-vs-code-agent-host-as-open-architecture-for-persistent-ai-sessions.aspx)（8/26）。

## 細節說明

### Cloudflare DNS 快取最佳化的技術細節

這五項最佳化值得逐一拆解，因為每一項都是 Rust 資料結構設計的直接教材。

**`Vec`/`String` 改 `Box<[T]>`/`Box<str>`。** 快取條目存入後不可變，`Vec` 為未來增長預留的 capacity 完全浪費。兩者在 64-bit 平台上的記憶體佈局差異：

```rust
// 改前：Vec<String> — 每個欄位 24 bytes（ptr + len + capacity）
struct EntryBefore {
    domains: Vec<String>,   // 24 bytes + heap
    // ... 其餘欄位
}

// 改後：Box<[Box<str>]> — 每個欄位 16 bytes（ptr + len），capacity 歸零
struct EntryAfter {
    domains: Box<[Box<str>]>,   // 16 bytes + heap
    // ... 其餘欄位
}
```

8 個欄位各省 8 bytes，合計每筆省 64 bytes，2,500 億筆即超過 15TB。

**Section 合併。** DNS 回應的 answer、authority、additional 三個 section 原本各自為 list；合併成單一 list 後用兩個 `u16` offset 標記邊界：

```rust
// 改前：三個獨立 Vec，各付 24 bytes 的 (ptr, len, capacity)
sections: (Vec<Record>, Vec<Record>, Vec<Record>)   // 72 bytes

// 改後：單一 Vec + 兩個 u16 邊界，共 20 bytes
struct Sections {
    records: Vec<Record>,      // 24 bytes（唯一一份）
    authority_end: u16,        // 2 bytes — answer 區結束位置
    additional_end: u16,       // 2 bytes — authority 區結束位置
}
```

每筆省 28 bytes（72 減去 24 加 4，再算上 Vec 本身的縮減）。

**Enum boxing。** Rust enum 的大小等於最大 variant。小小的 A record（4 bytes）被迫佔用 NAPTR 級距的 144 bytes：

```rust
// 改前：enum 大小 = 最大 variant，所有記錄都付 144 bytes
enum RDataBefore {
    A([u8; 4]),        // 4 bytes
    Naptr(NaptrData),  // 144 bytes → enum 大小被撐到 ~144 bytes
}

// 改後：大 variant 移到 heap，enum 本體只剩指標級大小
enum RDataAfter {
    A([u8; 4]),             // 直接內聯，零額外成本
    Naptr(Box<NaptrData>),  // 8 bytes 指標，實體在 heap
}
```

A/AAAA 每筆省 120 bytes（兩者占流量 80% 以上）；代價是 NAPTR 等罕見記錄反而多付一次 heap 配置，屬於划算的 trade-off。

**Raw wire-format 儲存。** 記錄資料直接以 DNS wire format bytes 存進單一 `Box<[u8]>`（2-byte 長度前綴加原始 bytes）：

```rust
// heap 中的實際佈局：
// [len_hi, len_lo, <原始 DNS wire bytes...>]
// 回應時 A/AAAA/TXT/DNSSEC 可直接把這段 bytes 複製進回應封包，
// 跳過逐欄位重新序列化。
```

僅含 domain name 的 CNAME/NS/MX/SOA 仍需解析，以套用 name compression。此步驟讓查詢延遲再降 5%。

**Scratchspace buffer。** 用跨插入重複使用的暫存 buffer 建構資料，完成後一次性 `memcpy` 進單一配置，取代每筆記錄各自的 heap 配置，插入吞吐量因此提升 13%。

驗證方式同樣值得學：自訂 allocator 包裝 Rust `System` allocator 逐筆記錄配置量；benchmark 用與生產流量相符的分佈（56% A、25% AAAA、19% TXT）填充快取；生產環境以 p90/p98/p99 追蹤，p99 記憶體從 9.3GB 降至 5.3GB（-43%）。釋出的 100TB 將轉投資快取容量以提升命中率。

### mklinux 的架構與效能數據

mklinux 的核心設計原則是「spawn kernel 不應比裸機多付出任何代價」。實例以 device tree 宣告（寫入 `/sys/fs/multikernel/`），device tree overlay 可在不重開機的情況下於資源池與執行中實例之間搬移記憶體、CPU 與裝置。實例可關閉、回收資源、再以不同 kernel 版本重生。

效能驗證在 dual-socket Xeon Gold 5418Y（Sapphire Rapids、2×24 cores、SMT 關閉）上進行，`will-it-scale` process 模式 24 tasks 單 socket：一個 kernel 驅動 24 cores 與兩個 spawn kernel 各 12 cores 比較，unlink1 從 300K/s 到 780K/s（2.60x）、rename1 達 1.69M/s（2.14x）、stat2 達 19.8M/s（2.10x）。getppid、futex、poll 等控制組工作負載維持 1.00x，證明加速來自 kernel 內部鎖競爭的消除而非測量假象。穩定性方面已通過長時間 soak loop：含 KASLR 與 5-level paging、spawn kernel panic 不會波及其他 kernel、實例的每顆 CPU 確認歸還 host 後才會重用。

[Phoronix 已公布與 KVM 的 2 vCPU 對比 benchmark 圖表](https://www.phoronix.com/news/Linux-7.0-mk2-Multikernel)。官方明確的應用模式是「app-kernel 與 device-kernel 分離」：一個實例專門跑驅動與 I/O，應用 kernel 完全看不到裝置中斷。目前限制：僅 x86_64、未進 mainline（Phoronix 評估短期內不太可能），以及生態系工具（容器 runtime、orchestrator）都還不存在。

### Asahi Linux 7.2 進度報告的重點

M3 系列的突破在於三個硬體改動的逆向工程。Apple 從 M3 Pro/Max 起把 USB port controller 從 I2C 匯流的 CD3217（ACE2）換成 SPMI 匯流的 ACE3，開發者發現 ACE3 的暫存器集幾乎與 ACE2 相同，只是包了不同介面，補上 SPMI 支援後 USB 3.0 與 Thunderbolt 全線打通。音訊方面 M3 新增「High Frequency」decimator，需要新的濾波係數與更大的初始化訊息；webcam 則只是 M3 Max 跳過了一條驅動未預期的初始化訊息。

更前瞻的部分：M3 的 GPU/DCP 韌體 ABI 對準 macOS 14.8.3，DCP 顯示支援已接近 M1/M2（macOS 13.5 ABI）的功能等級，官方 release「數週內」就會宣布。M4/M5 的 bring-up 也同時展開，macOS 15.x 韌體包改了 NVMe 控制器初始化序列，Yureka 與 Sven 在 m1n1 與 kernel 兩側完成修正後 NVMe 已可運作，PCIe 裝置枚舉與多核開機 crash 也已解決。硬體影片解碼（AVD）方面，AVC/HEVC/VP9 在所有支援機器上可靠運作，透過 fork 自 Bootlin 的 VA-API→V4L2 Stateless 轉譯層接入桌面應用。direct scanout（解碼幀直送顯示控制器、GPU 完全斷電）的 Interchange framebuffer 格式已在 DCP 驅動與 Mesa 兩側接好，只等 KWin 把 AGX/DCP 視為 multi-GPU 而停用 DMA-BUF 的限制解除（[Linuxiac 報導](https://linuxiac.com/asahi-linux-nears-official-support-for-apple-m3-macs/)，Plasma 6.8 可能支援）。

### VS Code Agent Host 的協議設計

AHP 的架構核心是「host 擁有權威狀態，client 是可來可去的觀察者與控制器」。每個 client 訂閱以 URI 定址的 channel（sessions、chats、terminals、changesets），收到初始狀態快照後接有序 action 序列；斷線重連時補發遺漏的 action 或重新拿快照。Session 資料用 immutable state 加 pure reducers 保證多 client 同步的一致性。本地場景 host 是 VS Code utility process（message port IPC），遠端場景是獨立 server（JSON-RPC over WebSocket，`code agent host --tunnel`）。不同 agent harness（Copilot 用 Copilot SDK、Claude 用 Claude Agent SDK）透過 adapter 翻譯成共同 session model。[官方架構文件](https://github.com/microsoft/vscode-docs/blob/main/docs/agents/concepts/agent-host.md)有完整細節。

一個值得注意的取捨：VS Code 原本推進中的 sandboxing rollout（已到 50%）被主動調回 0%，官方說法是為了聚焦 agent host 與 Copilot harness 的高優先級投資。大型專案裡公開降低另一條線的優先級，這種表態並不常見。
